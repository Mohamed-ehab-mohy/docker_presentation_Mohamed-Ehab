٠ الخطوة الصفرية — ملف الـ .dockerignore

قبل ما تكتب سطر واحد في الـ Dockerfile، في ملف صغير لازم يتعمل الأول — لو نسيته، الـ Image هتاخد وقت طويل في البناء، وفي حالات ممكن يضرب كراش كامل.

// diagram — ليه الـ .dockerignore ضروري قبل الـ COPY

Node.js

node_modules/
.env
*.log
.git

.NET

bin/
obj/
*.user
.vs/
🔥

سبب الكراش على الـ .NET: الـ bin/ وobj/ بيكونوا مبنيين على Windows، والكانتينر جواه Linux. الـ DLLs دي مش هتشتغل على معمارية تانية — الـ Container هيضرب كراش فوراً لو اتنسخوا.

١ Dockerfile — مشروع Node.js سطر بسطر

الـ Dockerfile عبارة عن "وصفة" بنكتبها للدوكر — بنقوله فيها خطوة خطوة إزاي يبني الـ Image اللي جوا فيها مشروعنا. كل سطر بيكوّن Layer مستقل.

// diagram — Layer Caching — ليه COPY package.json قبل COPY . .
١ Base Image — بيئة Linux خفيفة فيها Node Dockerfile 
FROM node:20-alpine   # روح هات Linux خفيف + Node.js v20 جاهز
٢ WORKDIR — مجلد الشغل داخل الكانتينر Dockerfile 
WORKDIR /app         # اعمل فولدر /app واجعله المجلد الرئيسي
                     # أي أمر جاي هيتنفذ من جواه
٣ COPY package.json أولاً — سر الـ Layer Caching Dockerfile 
COPY package*.json ./   # انسخ package.json و package-lock.json بس
RUN npm install         # نزّل المكتبات — layer مستقلة في الكاش
                         # لو package.json ما اتغيرش، السطر ده من الكاش ⚡
٤ COPY الكود — بعد ما المكتبات اتنزلت Dockerfile 
COPY . .   # انسخ كل كود المشروع (.dockerignore هيحجب node_modules)
٥ EXPOSE و CMD — توثيق ثم تشغيل Dockerfile 
EXPOSE 3000                       # توثيق فقط — الـ App بتسمع على البورت ده
CMD ["node", "server.js"]       # الأمر اللي هيشتغل لما الكانتينر يقوم
                                   # RUN = وقت البناء | CMD = وقت التشغيل
FROM بداية كل Dockerfile — بتحدد الـ Base Image اللي هتبني عليها. alpine = نسخة Linux خفيفة جداً.
WORKDIR بيعمل مجلد جوه الكانتينر ويخليه الـ current directory لكل الأوامر الجاية. بيمنع الفوضى في الـ root.
COPY بينسخ ملفات من جهازك لجوه الكانتينر. الترتيب مهم جداً بسبب الـ Layer Caching.
RUN بيشغّل أمر وقت بناء الـ Image. الناتج بيتحفظ كـ Layer في الكاش.
CMD الأمر اللي بيتشغّل وقت تشغيل الكانتينر — مش وقت البناء. ممكن يتـ Override من بره.

٢ Dockerfile .NET — Multi-stage Build

في الـ .NET الكود C# لازم يتعمل Compile لـ DLL قبل ما يشتغل. لو استخدمنا الـ SDK الكامل في الـ Production، الـ Image هتوصل لـ 1 جيجا. الحل هو تقسيم الـ Dockerfile لمرحلتين.

// diagram — Multi-stage Build — مطبخ مؤقت + بيئة خفيفة نهائية
١ Build Stage — SDK ضخم كـ "مطبخ مؤقت" Dockerfile 
# ── المرحلة الأولى: بيئة البناء ──────────────────────────────
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build-env
#    ↑ SDK كامل ~700MB               ↑ اسم مستعار نستخدمه بعدين
WORKDIR /src

COPY DotnetApp.csproj ./              # انسخ ملف المشروع بس الأول
RUN dotnet restore                    # نزّل NuGet Packages — Layer كاش

COPY . ./                             # دلوقتي انسخ كل الكود
RUN dotnet publish -c Release -o /app/out
#                   ↑ Release mode  ↑ اكتب الـ Output هنا
٢ Run Stage — Runtime خفيف + سرقة الناتج من المرحلة الأولى Dockerfile 
# ── المرحلة الثانية: بيئة التشغيل ───────────────────────────
FROM mcr.microsoft.com/dotnet/aspnet:8.0
#    ↑ Runtime بس ~100MB — مفيش Compiler هنا
WORKDIR /app

COPY --from=build-env /app/out .
#    ↑ روح للمرحلة الأولى وخد الـ Output منها
#    الـ SDK الـ 700MB اترمى في الزبالة — ما بيجيش في الـ Image النهائية

EXPOSE 8080
ENTRYPOINT ["dotnet", "DotnetApp.dll"]
#  ↑ ENTRYPOINT = أمر ثابت مش ممكن يتغير بالخطأ من بره (أقوى من CMD)
📊

النتيجة العملية للـ Multi-stage Build: الـ Image النهائية بتنزل من ~1 GB لـ ~200 MB — لأن الـ SDK الكامل وكل ملفات البناء بتتمسح بشكل أوتوماتيكي ومش بتيجي في الـ Image النهائية.

٣ Build & Run — من الكود لكانتينر شغّال

الـ Dockerfile كتالوج مكتوب بس — عشان يتحوّل لـ Image حقيقية وبعدين كانتينر شغّال، بنستخدم أمرين أساسيين.

// diagram — تشريح أمر docker build
١ بناء الـ Image لكل مشروع Terminal 
# مشروع Node.js
docker build -t node-api .

# مشروع .NET (من داخل فولدر المشروع)
docker build -t dotnet-api .
٢ التحقق من الـ Layer Caching Terminal Output 
# لما تشوف ده في الـ Terminal:
 => CACHED [2/5] WORKDIR /app                          0.0s
 => CACHED [3/5] COPY package*.json ./                 0.0s
 => CACHED [4/5] RUN npm install                       0.0s
 => [5/5] COPY . .                                     0.3s

# ده معناه: بس السطر الأخير اتنفذ من أول — الباقي من الكاش ⚡
٣ تشغيل الـ Image كـ Container Terminal 
docker run -d  -p 5000:3000  --name my-node-container  node-api
#          ↑   ↑             ↑                          ↑
#       خلفية  Ports     اسم الكانتينر             اسم الـ Image
-t node-api -t = Tag. بنسمي الـ Image اسم مفهوم بدل رقم عشوائي. بعدين نكتب الاسم ده في docker run.
-d Detached Mode — الكانتينر يشتغل في الخلفية ويسيب الـ Terminal حر. بدونها الـ Terminal بيتـ lock.
--name اسم دلع للكانتينر الشغّال — بيسهّل الـ docker stop وdocker rm بعدين.
docker ps يعرض كشف بكل الكانتينرات الشغالة حالياً مع البورتات والأسماء والـ IDs.

٤ Port Mapping — فك لغز العزلة

الكانتينر لما يقوم بيبقى معزول تماماً — ملوش باب على العالم الخارجي. الـ Port Mapping هو اللي بيفتحله نافذة يطل منها.

// diagram — الـ -p كـ "ماسورة" بين جهازك والكانتينر
Node تشغيل Node API — جهازك:5000 → الكانتينر:3000 Terminal 
docker run -d -p 5000:3000 --name my-node-container node-api
#              ↑    ↑
#         HOST:5000  CONTAINER:3000
# افتح المتصفح على: http://localhost:5000
.NET تشغيل .NET API — جهازك:8080 → الكانتينر:8080 Terminal 
docker run -d -p 8080:8080 --name my-dotnet-container dotnet-api
# افتح المتصفح على: http://localhost:8080
الـ -p HOST:CONTAINER زي الماسورة — الطلب بيجي من المتصفح على البورت بتاع جهازك، الماسورة بتحدفه جوه الكانتينر على البورت الداخلي. الكانتينر نفسه ما يعرفش إنه معزول — يشوف الطلب جاي عادي.

٥ Volumes — الداتا لازم تعيش بعد الكانتينر

في قاعدة ذهبية في Docker: Containers are ephemeral — الكانتينرات كائنات مؤقتة. أي داتا بتتكتب جواها، لو الكانتينر اتمسح، الداتا بتتمسح معاه للأبد.

// diagram — الكارثة بدون Volumes والحل بيها
١ إثبات الكارثة — ادخل الكانتينر واكتب ملف ثم امسحه Terminal 
# ادخل جوه الكانتينر الشغّال
docker exec -it my-node-container sh

# اكتب ملف جوا
echo "Mohamed Ehab was here" > data.txt
exit

# امسح الكانتينر كامل
docker stop my-node-container
docker rm my-node-container

# شغّل كانتينر جديد وافتش على الملف
docker run -d -p 5000:3000 --name my-node-container node-api
docker exec -it my-node-container ls
# data.txt مش موجود — الداتا راحت 💀
٢ إنشاء Volume وربطه بالكانتينر Terminal 
# إنشاء Volume مستقل
docker volume create my-secure-data

# شغّل الكانتينر مع الـ Volume
docker run -d -p 5000:3000 \
  -v my-secure-data:/app/data \
  --name my-node-container node-api
#  ↑
#  my-secure-data (على جهازك) ↔ /app/data (جوه الكانتينر)
٣ الإثبات — امسح الكانتينر وشوف الداتا لسه موجودة Terminal 
# اكتب داتا جوه فولدر الـ Volume
docker exec -it my-node-container sh
cd data && echo "Database is safe now!" > backup.txt
exit

# امسح الكانتينر تماماً
docker stop my-node-container && docker rm my-node-container

# شغّل كانتينر جديد بنفس الـ Volume
docker run -d -p 5000:3000 \
  -v my-secure-data:/app/data \
  --name my-new-container node-api

# افتش على الداتا
docker exec -it my-new-container cat /app/data/backup.txt
# Output: Database is safe now! 🎉
💡

ده نفس التكنيك اللي بنأمن بيه SQL Server وMongoDB في الشغل الحقيقي. الـ Database Container ممكن يتمسح ويتعمل Update — والداتا مش هتتأثر لأنها في Volume منفصل.

٦ Environment Variables — إعدادات ديناميكية بدون Build جديد

بدل ما نكتب الـ Connection Strings والبورتات جوه الكود مباشرة (Hardcoded)، بنخلي الدوكر يـ inject القيم دي من بره وقت التشغيل — من غير ما نفتح الـ VS Code ونعمل Build جديدة.

// diagram — حقن Environment Variables من بره الكانتينر
Node تغيير البورت ديناميكياً بدون Build جديدة Terminal 
# الكود بياخد البورت من env: process.env.PORT || 3000
docker run -d -p 8000:7000 -e PORT=7000 --name node-dynamic node-api
#                           ↑
#    حقنّا PORT=7000 جوه الكانتينر — الـ Node هيقرأه أوتوماتيك
# افتح: http://localhost:8000
.NET تغيير الـ Connection String بالـ Double Underscore Terminal 
docker run -d -p 8080:8080 \
  -e ConnectionStrings__DefaultConnection="Server=LiveServer;Database=SchoolDb;User Id=sa;Password=StrongPass!;" \
  dotnet-api
#              ↑
# ConnectionStrings:DefaultConnection في appsettings.json
# بيتكتب في الـ env بـ __ (Double Underscore) بدل : (Colon)
# لأن الـ Linux مش بيفهم : في أسماء المتغيرات
🔑

تريكة الـ __ (Double Underscore): في الـ appsettings.json المفاتيح بتبقى متداخلة ConnectionStrings:DefaultConnection. الـ Linux مش بيسمح بـ : في أسماء المتغيرات، فبنستبدلها بـ __ — والـ .NET بيفهمها أوتوماتيك.

🧹 نظّف جهازك — أمر الـ Docker Prune

كل مرة بتعمل docker build بعد تعديل، الـ Layers القديمة بتفضل على الهارد كـ "Dangling Images" — بتاكل مساحة في صمت.

docker system prune -a --volumes
# -a         → امسح كل الـ Images الميتة مش مربوطة بكانتينر شغّال
# --volumes  → امسح الـ Volumes القديمة المهجورة
# النتيجة: Total reclaimed space: XX GB
# ⚠️ هيمسح الـ Volumes كمان — احرص مش تشغّله على Production

٧ Docker Compose — السيستم كله بأمر واحد

لو مشروعك فيه API + قاعدة بيانات + Cache Redis، هتكتب docker run لكل واحد، وتربط الـ Networks والـ Volumes يدوياً؟ الـ Docker Compose بيحل ده بملف YAML واحد.

// diagram — Bridge Network الأوتوماتيكي وسر الـ Service Name كـ DNS
١ خدمة قاعدة البيانات — SQL Server جاهز docker-compose.yml 
version: '3.8'

services:

  database:                                  # الاسم ده = الـ DNS جوه الشبكة
    image: mcr.microsoft.com/mssql/server:2022-latest
    container_name: mssql_db
    ports:
      - "1433:1433"
    environment:
      - ACCEPT_EULA=Y
      - MSSQL_SA_PASSWORD=YourStrongPassword123!
    volumes:
      - db_data:/var/opt/mssql             # الداتا محفوظة خارج الكانتينر
٢ خدمة الـ API + depends_on + Connection String السحرية docker-compose.yml 
  my-api:
    build:
      context: ./dotnet-app             # فولدر المشروع
      dockerfile: Dockerfile            # الـ Dockerfile جواه
    container_name: school_api
    ports:
      - "5000:8080"
    environment:
      - ConnectionStrings__DefaultConnection=Server=database;Database=SchoolDb;User Id=sa;Password=YourStrongPassword123!;Encrypt=False;
      #                                                    ↑
      #                                    اسم الـ Service مش localhost!
    depends_on:
      - database                           # اوعى تقوم غير لما database يقوم الأول
٣ تعريف الـ Volume المستمر في آخر الملف docker-compose.yml 
volumes:
  db_data:   # تعريف الـ Volume على مستوى الـ Compose
             # الدوكر هيعمله لو مش موجود، وهيبقى مستمر بين الـ Runs
٤ أوامر التشغيل والإيقاف Terminal 
# شغّل السيستم كله (مع بناء الـ Images)
docker compose up --build

# شغّل في الخلفية
docker compose up --build -d

# وقف كل حاجة + امسح الكانتينرات + الشبكات
docker compose down

# شوف الـ Logs لخدمة معينة
docker compose logs my-api
سر الـ Bridge Network: بمجرد docker compose up، الدوكر بيعمل شبكة افتراضية خاصة وبيضيف كل الكانتينرات فيها. كل كانتينر ممكن يكلم التاني باسم الـ Service مباشرة — الدوكر بيترجمه لـ IP تلقائياً. مش محتاج localhost ولا IP ثابت.
⚠️

الكمين الشهير: لو كتبت Server=localhost في الـ Connection String جوه الـ Compose، الـ API هتفتش عن الـ DB جوا الكانتينر بتاعها هي — ومش هتلاقيها. الصح هو Server=database — اسم الـ Service بالظبط.

٨ Quick Reference — Cheat Sheet

الأمر / المفهوم بيعمل إيه؟ متى تستخدمه؟
.dockerignore يحجب ملفات من الـ COPY قبل ما تكتب سطر في الـ Dockerfile
FROM image:tag AS name يبدأ Stage جديد بـ Base Image أول سطر في كل Stage
COPY package*.json ./ + RUN install Layer Caching للـ Dependencies قبل COPY . . دايماً
COPY --from=build-env /out . ينقل ناتج Stage لـ Stage في الـ Multi-stage Run Stage
docker build -t name . يبني Image من الـ Dockerfile أول مرة أو بعد تغيير الكود
docker run -d -p H:C --name n img يشغّل Container من Image كل مرة تحتاج تشغّل التطبيق
-p 5000:3000 Port Mapping HOST:CONTAINER عشان المتصفح يوصل للـ API
docker volume create name ينشئ Volume مستقل قبل تشغيل أي Container بيكتب داتا
-v vol:/app/data يربط Volume بمجلد جوه الكانتينر في أمر docker run
-e KEY=VALUE يحقن Environment Variable لتغيير الإعدادات بدون Build جديدة
ConnectionStrings__Key : → __ للـ .NET في Linux في الـ Compose env أو docker run -e
Server=database (في Compose) اسم الـ Service كـ DNS في أي Connection String جوه Compose
depends_on: - service يأخر قيام Service لحد ما التانية تقوم لما الـ API تحتاج الـ DB يكون جاهز
docker compose up --build يبني ويشغّل كل السيستم أسرع طريقة لتشغيل المشروع كامل
docker compose down يوقف ويمسح الكانتينرات والشبكات لما تخلص أو تعمل Cleanup
docker system prune -a --volumes ينظف كل الـ Images والـ Volumes الميتة أسبوعياً لاسترداد مساحة الهارد
